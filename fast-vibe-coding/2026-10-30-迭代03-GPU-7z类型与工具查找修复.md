## 1. 背景

打包产物使用 `TestData/4.7z` 实测时，信息面板显示「加速方式 CPU」，GPU 从未被使用。
排查确认不是显卡或驱动问题：`hashcat -I` 能正确识别 AMD Radeon RX 6650 XT，
同机 `SecretHeader.7z` 可以正常走 GPU 破解。

## 2. 根因（均已复现）

### 2.1 `$7z$` 的 data_type 被误判

`4.7z` 是 header 加密，7z2hashcat 输出：

```text
$7z$1$19$0$$16$...$208$193$...
```

`data_type` 的真实含义是**加密头解密后的压缩方法**：
0=原始、1=LZMA1、2=LZMA2、7=DEFLATE，hashcat 11600 全部支持。
旧实现把 1 当成「普通 7z」而只接受 0，于是 4.7z 被判为「格式不支持 GPU」。

实测：同一条 `$7z$1$` 直接交给 hashcat 可正常解析并运行；
`SecretHeader.7z`（type 0）在同机 GPU 上破解成功，证明 GPU 链路本身正常。

### 2.2 工具在子目录

打包目录为：

```text
publish\
  ArchivePasswordTestTool.exe
  hashcat-6.2.6\
    hashcat.exe
    7z2hashcat64-2.0.exe
    OpenCL\ modules\ ...
```

旧实现只查 `AppContext.BaseDirectory\hashcat.exe`，从 publish 根目录运行会提示
「未在程序目录找到 GPU 工具」。

### 2.3 小字典静默走 CPU

默认 7z 阈值 25,000 行；`TestData/BigDictionary.txt` 只有 2,100 行，
旧实现既不探测 hashcat，也不输出任何原因，容易被误认为 GPU 功能损坏。
实测 2,100 行走 CPU 约 512 个/秒（4.1 秒）；GPU 固定启动成本约 8–13 秒，
这个规模 CPU 确实更快，阈值本身合理。

### 2.4 hashcat 11600 在大字典下崩溃（外部依赖）

修复 2.1/2.2 后，4.7z 已能选中 GPU，但 hashcat 6.2.6 在 14,459,679 行字典下
运行到约 1–3% 时崩溃（访问冲突，工作线程），程序按设计回退 CPU。
同样的崩溃在 type 0 的 `SecretHeader.7z` 上也能复现，说明不是 LZMA1 专属问题；
100,000 / 500,000 行时 6.2.6 正常。

用 **hashcat 7.1.2** 复现后拿到完整栈：

```text
module_11600.dll module_hash_encode() -> vsnprintf()/msvcrt
```

即崩溃发生在 **hash 编码**（状态显示 / potfile 写入）路径，而不是 GPU 内核。
`4.7z` 的 7z 哈希 salt 长度为 0（`$7z$1$19$0$$16$...`），
`module_hash_encode` 用 `%s` 输出 `seven_zip->salt_buf`，零长度 salt 时该缓冲区
没有保证的终止符，属于 hashcat 模块侧缺陷。6.2.6 与 7.1.2 都存在。

对策：会话使用 `--quiet` + `--potfile-disable`（本工具本来也不需要 potfile，
候选由 7z.dll 确认），并加 120 秒无进展看门狗。

**hashcat 8.0.0 兼容**：8.0.0 移除了 `--stdin`（改为 `-a 0` 且不提供 wordlist 时读 stdin），
且 `--quiet` 不再抑制状态屏；状态打印会调用 `module_hash_encode`。程序按版本选择参数：
6.x/7.x 用 `--stdin`，8.x 用 `-a 0` + `--status-timer 3600`。8.0.0 的 100k 分块已跑通。

## 3. 决策

| 编号 | 决策点 | 结论 |
| ---- | ------ | ---- |
| D1 | `$7z$` 类型校验 | 按 hashcat 支持的 data_type 集合 `{0,1,2,7}` 校验；header 判定仍用 `ArchiveInfo.IsHeaderEncryption` |
| D2 | 工具查找 | 程序目录 → 一级子目录；不递归、不搜 PATH/注册表（取代迭代 02 D5 的「仅 exe 同目录」） |
| D3 | 小字典提示 | 保留 25,000 / 500,000 阈值，新增「低于阈值」提示 |
| D4 | hashcat 版本 | 仍接受 6.x，但文档建议使用 7.x；6.2.6 在超大字典下存在崩溃风险 |
| D5 | 结果确认 | 不变：hashcat 候选仍由 7z.dll 最终确认 |

## 5. 验证

- `dotnet test -c Debug`：**213 通过 / 0 失败**（迭代 02 为 195，新增 18）。
- 打包 AOT 产物：
  - `4.7z` + 100,000 行：面板显示 `GPU · AMD Radeon RX 6650 XT · hashcat 7.1.2`，正常结束；
  - `4.7z` + 500,000 行：同一路径正常结束；
  - `4.7z` + 1,000,000 行（7.1.2 + `--potfile-disable`）：约 14% 处无进展，看门狗回退 CPU；
  - 对照：hashcat 6.2.6 / 7.1.2 + 14,459,679 行均在约 1–3% 崩溃
    （`module_hash_encode → vsnprintf`），回退 CPU。
- **hashcat 8.0.0**（用户提供）：
  - 100,000 行分块：完成（exit 1），未崩溃；
  - 1,000,000 行（`-a 0` + `--status-timer 3600` + `--potfile-disable`）：
    **完整跑完**（exit 1），未崩溃/未挂起；
  - **App + 8.0.0 + 完整 14,459,679 行**：面板显示
    `GPU · AMD Radeon RX 6650 XT · hashcat 8.0.0`，**01:01:25 跑完全部 14,459,679 个密码**
    （3,924 个/秒），无崩溃/无回退；结果为「未找到正确的解压密码」
    → **该字典不含 4.7z 的密码**。
  - **正向命中验证**：最终 AOT + 8.0.0 + `SecretHeader.7z` + `DictOK.txt` →
    `GPU · ... · hashcat 8.0.0`，找到 `Correct123!`，并经 7z.dll 确认。
- 子目录查找：从 publish 根目录运行、hashcat 位于 `hashcat-6.2.6\` 时能正确选中。
- 低于阈值提示：`APTT_GPU_MIN=1000000` + 2,100 行字典时输出提示并保持 CPU。
- 最终 AOT + 10,000 行：面板显示 GPU / 7.1.2；hashcat 报 `Insufficient memory available`
  后按预期回退 CPU，未挂起、无会话残留。
- 结论：**GPU 启用链路已修复**（4.7z 的 type 1 不再被误判，工具子目录可发现）；
  8.0.0 配合 `--status-timer 3600` + `--potfile-disable` 可稳定跑完整 14.45M 字典。
- 4.7z 的密码**不在** `hashmob.net_2025.medium.found` 中；如需 4.7z 的正向命中，
  需提供正确密码或包含它的字典。

> 4.7z 的真实密码命中结果与完整字典耗时在本次会话中记录。

## 6. 备注

- hashcat 7.1.2 的 `-I` 输出为 `Backend Device ID #01`（两位数字），
  `LeadingNumber` 解析为 `01`，`-d 1` 仍正确。
- hashcat 6.2.6 崩溃是外部依赖问题，不在本工具内修复；建议随包升级到 7.x。
- 7z2hashcat 仍只从程序目录（含一级子目录）查找，不随程序分发。
